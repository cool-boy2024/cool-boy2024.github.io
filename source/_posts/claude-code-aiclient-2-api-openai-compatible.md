这篇是上一篇 AIClient-2-API 教程的**补充篇**。

上一篇的重点，是先把 `openai-codex-oauth` 跑通，拿到一个本地可调用的 OpenAI 兼容接口。到了这一步，很多人下一个问题就会变成：**我能不能让 Claude Code 直接吃这个接口，然后继续帮我写文章、整理 Markdown、准备发博客？**

这篇就是专门解决这个问题的。

不过这篇不会重讲 Docker、代理、授权这些环境准备。默认前提是：你已经按上一篇把 AIClient-2-API 跑起来了，并且能直接测通本地接口。

## 这篇文章到底帮你完成什么

如果你只关心结果，这篇文章要帮你完成 4 件事：

1. 先搞清楚 Claude Code 和 AIClient-2-API 在这条链路里分别负责什么
2. 把已经跑通的 OpenAI 兼容接口整理成 Claude Code 可复用的信息
3. 让 Claude Code 继续帮你生成、整理和检查 Hexo 博客文章
4. 在你确认之后，再决定是否执行推送发布

这里最重要的一点是：

**Claude Code 不是直接连网页模型，它连的是 AIClient-2-API 暴露出来的 OpenAI 兼容接口。**

## 先把心智模型理顺

别一上来就想着“Claude 调 OpenAI 网页模型”。这句话太容易把自己绕进去。

更准确的理解方式应该是：

```text
Claude Code -> OpenAI 兼容接口 -> AIClient-2-API -> 网页侧授权能力
```

这条链路里，每一层只干一件事：

- **Claude Code**：负责理解你的任务、生成内容、改文章、协助发布
- **OpenAI 兼容接口**：负责提供一个标准调用入口
- **AIClient-2-API**：负责把网页授权能力整理成这个标准入口
- **网页侧授权能力**：负责真正提供账号可用的模型能力

这样想的好处是，排错时不会把问题混在一起。

如果 Claude Code 没法正常帮你干活，你第一反应不应该是“Claude 不行”，而是先问：

- 接口本身通了吗？
- `base_url` 对了吗？
- `model` 对了吗？
- 你给 Claude 的是不是正确那一组值？

## 使用前提：这篇不从 0 开始

你至少要先具备下面这些条件：

- 你的 Windows 电脑上已经能正常使用 Claude Code
- 你的 AIClient-2-API 已经在本地跑起来了
- 你已经能直接测试 OpenAI 兼容接口
- 你已经有 Hexo 博客目录
- 你知道自己的私密信息应该自己填，不要让 AI 替你编

如果你还没跑到这一步，先回上一篇把最基础的接口打通。

## 先分清楚：哪些值可以公开写，哪些必须你自己填

这一节非常重要。

很多小白卡住，不是因为不会配，而是因为把“示例值”和“真实值”混在一起了。AI 也很容易在这一步帮倒忙。

### 可以公开写的默认值

下面这些东西，通常可以直接写进文章、提示词、示例命令里：

- OpenAI 兼容接口的格式
- 常见的本地地址格式
- 示例模型名
- Hexo 文章目录示例
- 文章 frontmatter 模板
- 检查命令模板

比如你已经很熟悉的这种格式：

```text
http://127.0.0.1:3000/openai-codex-oauth/v1
```

它可以当作**示例接口格式**出现。

### 必须由你自己填写的私密值

下面这些值，不要让文章直接替你写死，也不要让 AI 自作主张乱填：

- `<你的真实 API Key>`
- `<你的 token 或 cookie>`
- `<你的博客仓库路径>`
- `<你的 Git 身份信息>`
- `<你的仓库远程地址>`
- `<你的文章真实标题>`
- `<你的个人信息或账号信息>`

你可以把这条规则记死：

**公开默认值可以照着改，私密值只能你自己填。**

## Claude Code 真正要吃进去的，其实只有 3 个核心值

如果上一篇你已经跑通了，那么对 Claude Code 来说，真正关键的通常就是下面这 3 个值：

- `base_url`
- `api_key`
- `model`

你可以先把它们整理成下面这种形式：

```text
Base URL: http://127.0.0.1:3000/openai-codex-oauth/v1
API Key: <你的本地 API Key>
Model: <你当前可用的模型名>
```

注意两点：

1. 这里的 `API Key` 应该是你**本地这层接口要求的 key**，不是让你把网页登录态直接塞给 Claude
2. `Model` 要以你当前这条接口实际能用的名字为准，不要想当然乱写

## 先验证 API，再考虑 Claude Code

这一步不要偷懒。

很多人一上来就想直接把配置喂给 Claude Code，结果后面一出错，根本不知道是 Claude 的问题，还是接口没通。

正确顺序应该是：

1. 先直接测试 OpenAI 兼容接口
2. 只有直测成功了，才继续用 Claude Code

最小验证思路很简单：

- 确认接口地址没写错
- 确认 key 没写错
- 确认 model 没写错
- 让接口返回一条最简单的回复

这一步的目标不是炫技，只是为了确认：

**你给 Claude Code 的那组值，本身就是能工作的。**

## 给小白用的固定配置块

下面这块不是让你无脑照抄到底，而是让你知道一套最小可用的信息结构应该长什么样。

```text
OpenAI-Compatible Base URL:
http://127.0.0.1:3000/openai-codex-oauth/v1

OpenAI-Compatible API Key:
<你的本地 API Key>

Model:
<你当前可用的模型名>

Hexo Blog Path:
<你的博客本地目录>

Target Post Path:
<你的博客本地目录>\source\_posts\<你的文章文件名>.md
```

这一块里：

- 第一行和接口格式可以参考上一篇
- API Key 必须你自己填
- 模型名必须以你本地实测成功的名字为准
- 博客路径也必须用你自己的实际路径

## Claude Code 的推荐使用顺序

如果你是想让 AI 直接帮你干活，而不是只看一篇教程，那就固定按这个顺序来。

### 第一步：先确认接口现在还是通的

先不要急着写文章。

你要先确认：上一篇里已经跑通的那条 OpenAI 兼容接口，现在依然可用。

因为只要这一步不稳，后面所有“Claude 帮我写博客”的流程都会变成假动作。

### 第二步：再让 Claude Code 读你的博客目录

当接口本身没问题之后，再把工作切换到博客目录。

你要让 Claude Code 知道：

- 你的博客是 Hexo 项目
- 文章目录在哪里
- 你要写的是“上一篇的补充篇”
- 风格要继续保持可执行、可复现、少废话

### 第三步：先让 Claude 生成草稿，不要先发

这一步最容易犯的错，是刚生成完就想发。

更稳的做法是：

1. 先生成文章草稿
2. 再检查标题、结构、frontmatter
3. 再检查有没有误写私密信息
4. 再决定要不要保存和发布

### 第四步：让 Claude 帮你整理成 Hexo 可发布格式

这一步 Claude 比较适合做的事情包括：

- 整理 Markdown 层级
- 补齐 frontmatter
- 调整标题和小节顺序
- 统一术语
- 把不该公开的值改成占位符
- 检查是不是明确说明“推送前要确认”

### 第五步：本地检查，再决定是否推送

只要你博客是走 GitHub Pages 自动发布，那“push”本身就是一个外部可见动作。

所以正确顺序一定是：

1. 先看文章文件
2. 再本地构建或预览
3. 确认内容无误
4. 最后才决定是否 push

## 给 Claude Code 生成文章的提示模板

如果你希望 Claude Code 直接接管这篇补充文的整理过程，可以把下面这段改一改直接用。

### 模板 1：生成补充篇草稿

```text
你现在在一个 Hexo 博客项目里工作。

我已经有一篇上一篇文章，主题是 AIClient-2-API 跑通 openai-codex-oauth 并提供 OpenAI 兼容接口。

现在请你帮我写一篇补充文章，目标是：说明如何让 Claude Code 继续使用这条 OpenAI 兼容接口来帮助我写博客文章，并在确认后协助发布。

要求：
1. 这是上一篇的补充篇，但正文要可独立阅读
2. 主线只围绕 AIClient-2-API，不扩展其他路线
3. 面向小白及给小白代操作的 AI 助手
4. 语言要直接、少废话、步骤清楚
5. 必须包含：心智模型、3 个核心值、固定配置块、AI 执行模板、最小排错清单、发布确认边界
6. 所有私密值都用占位符，不要编造真实值
7. 输出为适合 Hexo 的 Markdown 文章
```

### 模板 2：检查文章里有没有泄露私密值

```text
请帮我检查这篇 Hexo Markdown 文章，重点只看下面几件事：

1. 有没有把真实 API Key、token、cookie、仓库地址、Git 身份信息写进正文
2. 哪些值应该保留为公开默认值示例
3. 哪些值应该改成占位符
4. 有没有让读者误以为示例值可以直接当成真实值使用

如果发现问题，请先告诉我最可能的风险，再给我建议修改方式。
```

### 模板 3：发布前协助模板

```text
请帮我做博客发布前检查，但不要直接执行外部可见动作。

请按下面顺序协助我：
1. 检查文章 frontmatter 是否完整
2. 检查 Markdown 结构是否适合 Hexo
3. 检查有没有私密值泄露
4. 检查上一篇和补充篇之间的承接是否自然
5. 给出本地构建和预览建议
6. 如果一切正常，只给出建议执行的 git 命令，不要直接 push

在我没有明确确认前，不要替我执行推送发布。
```

## 最小排错清单：固定按这个顺序，不要跳步

这一节建议你以后也固定照着用。

### 1. 先测 OpenAI 兼容 API 本身是否通

**现象：** Claude Code 后续流程全都不稳定，或者文章生成能力异常。

**最可能原因：** 根本不是 Claude 的问题，而是你底层接口已经不通了。

**下一步动作：** 先回到最小 API 直测，确认 `base_url`、`api_key`、`model` 这一组值现在还是可用的。

### 2. 再检查 `base_url`

**现象：** 明明服务开着，但请求就是不对。

**最可能原因：** 你填错了路径，尤其是漏了 provider 路径段。

**下一步动作：** 回到上一篇里已经测通的那条完整接口地址，不要自己凭感觉改写。

### 3. 再检查 `model`

**现象：** 接口本身有响应，但模型调用不对、报不存在或行为异常。

**最可能原因：** 你给 Claude 的模型名和当前接口真正可用的模型名不一致。

**下一步动作：** 用你已经直测成功的模型名，不要临时乱换。

### 4. 再检查 token / cookie / key

**现象：** 配置看起来都对，但调用还是失败。

**最可能原因：** 认证信息过期、写错，或者把不该给 Claude 的值给错了地方。

**下一步动作：** 区分清楚：网页授权相关信息属于 AIClient-2-API 那层，本地兼容接口 key 属于 Claude 这层要吃的值。

### 5. 再检查本地端口 / 代理 / 目录

**现象：** 有时能用，有时不能用，或者博客文件根本改错目录。

**最可能原因：** 本地端口变了、代理影响了调用、Claude 读错了项目目录。

**下一步动作：** 确认接口端口、博客路径、当前工作目录是不是你真正想操作的那一个。

### 6. 最后看日志

**现象：** 前面几步都检查过了，还是说不通。

**最可能原因：** 真正的错误细节只在日志里。

**下一步动作：** 再回头看 AIClient-2-API 和相关命令输出，不要一边猜一边改。

## 把文章放进博客时，最稳的做法是什么

如果你已经让 Claude Code 帮你整理好了 Markdown，那么落到博客里最稳的步骤通常是：

1. 确认文件名
2. 确认 frontmatter
3. 存到 `source/_posts/`
4. 本地构建
5. 本地预览
6. 确认没问题后，再决定是否推送

比如你的目标文件大概会长成这样：

```text
<你的博客目录>\source\_posts\claude-code-aiclient-2-api-openai-compatible.md
```

## 发布边界一定要写清楚

这一节我建议你在以后所有“AI 帮我发文”的文章里都保留。

因为很多人一看到“AI 帮我生成并上传”，就默认理解成“AI 会自动帮我发出去”。

这不够稳。

更准确的说法应该是：

- Claude Code 可以帮你生成内容
- 可以帮你整理成 Hexo 可发布格式
- 可以帮你检查 frontmatter 和目录
- 可以帮你给出构建和 Git 命令建议
- **但真正的推送发布，必须在你确认之后再执行**

如果你的博客仓库配置的是“push 到 `main` 自动发布到 GitHub Pages”，那这条边界更不能省。

## 一句话总结

如果你只记住一句话，那就是：

**AIClient-2-API 负责把网页能力整理成 OpenAI 兼容接口，Claude Code 负责消费这个接口继续帮你写博客，而真正的发布动作必须由你确认后再执行。**
